# PB-24 统一管线决策分析（2026-08-30，决策条件已满足）

> 前置：IR 前端语法覆盖全量达成（`->` 指针成员访问 + `?:` 三元补齐，见 STAGE_SUMMARY §3.1）。
> 本文档为决策输入，最终走向由 ltree 定夺。

## 1. 决策问题

NihaoC 目前存在**两套独立编译管线**：

| | A 方案（parser.c） | B 方案（irparse.c → IR） |
| ---- | ---- | ---- |
| 定位 | 产品方向：全量 parser 单趟转 C 文本 | 语义验证器：平台中立 IR 中间层 |
| 输出 | C 文本 → tcc 编译 | IR → ir-c（C 文本）/ ir-native（自研 x86-64 asm）/ ir-riscv64 / ir-arm64 / ir-loongarch64 |
| 多平台 | 借助 tcc C 后端天然获得 | 自研各架构汇编后端（riscv64/arm64/loongarch 仅验汇编生成） |
| 测试 | c/native 12P | IR_SUBSET 24 例四后端一致 + IR_ONLY 6 例双后端 |

**PB-24 的核心问题**：这两条管线是继续并行（各司其职），还是合流（统一到某一前端）？合流的话以谁为主、B 方案各后端去留如何？

## 3. 三条路线评估

### 路线 1：维持双管线（现状+明确分工）
- 继续：A=产品化主线（C 输出 + tcc 全平台），B=语义验证器（IR 平台中立，验证语法/语义设计）
- 成本：两套 parser/两套测试维护（语法增量要改两处——`=>` 即先例）
- 收益：B 方案不绑定 A 方案的 C 输出细节，可独立演进为"语言语义规范的可执行规格"
- 风险：长期双维护稀释人力；B 方案 native 后端（x86-64）若持续无产品需求会变成"验证用死代码"

### 路线 2：合流到 B 方案（IR 为唯一前端）
- 单一 parser + 多后端（ir-c 保底、native 自研）
- 成本：需补 M2 静态检查、link 跨文件、类型化指针、布局内置函数——**工作量=重做 A 方案已完成的部分**；自研 native 后端覆盖全部平台（riscv64/arm64/loongarch）遥遥无期
- 收益：单一维护点；IR 利于后续优化（常量折叠/死代码消除）
- 风险：**产品交付时间大幅推迟**；自研汇编后端正确性风险高（x86-64 目前仅靠 30 个 IR 用例验证）

### 路线 3：以 B 方案为前端、C 输出为唯一产品后端（折中）
- parser 统一到 irparse.c，删掉 A 方案 parser.c；后端只留 ir-c（IR→C 文本→tcc 全平台）
- 成本：B 方案补齐 2.3 的差距（工作量中等，非"重做"）；ir-c 输出质量需达 A 方案水平
- 收益：单一 parser；多平台仍靠 tcc（不依赖自研汇编）；native 后端作为可选性能路径
- 风险：ir-c 生成的 C 文本目前是"平铺槽 tN"风格（`int64_t t1 = ...`），可读性/优化度不如 A 方案直接转 C；退化为"先转 IR 再转 C"的两步冗余

## 4. 战略分析（矛盾论视角）

**主要矛盾**：编译器价值在"**能用**"——把 NihaoC 程序编译成可运行产物，且多平台。这指向 A 方案（C 输出 + tcc）或路线 3（IR + C 输出）。

**次要矛盾**：语义正确性验证。B 方案当前的核心价值是作为"语言设计验证器"——IR 平台中立、可独立检查语法/语义，且已有 24+6 例一致性测试护航。

**矛盾转化**：当 B 方案补齐 2.3 差距后，"语义验证"矛盾会弱化，"统一维护"矛盾上升。但此刻 B 方案尚未补齐差距，**强行合流=用产品交付换架构整洁，投入产出不划算**。

**结论倾向**：**路线 1 延续 + 边界条件明确**——维持双管线，但定义"何时合流"的触发条件（而非无限期并行）；同时把 B 方案 2.3 差距按优先级消化（类型化指针是硬缺口，link/静态检查可缓）。

## 5. 推荐方案（分阶段）

**阶段 1（当下，0 风险）**：维持双管线，PB-24 标记"条件满足、维持再观察"。立项 B 方案**类型化指针模型**（补 `p = &标量` 声明，消 ir_arrow 的 IR_ONLY 归类）——这是 2.3 中唯一影响日常用例的硬缺口。

**阶段 2（触发条件=出现任一）**：
- 自研 native 后端（x86-64）达到可产品化质量（跑通真实程序 + 性能达标）→ 评估路线 2/3
- A 方案 parser 维护成本明显拖慢语法演进（如同一天改两处已成常态）→ 评估路线 3（IR 统一前端 + ir-c 输出）
- 出现明确的多平台"非 C 环境"需求（如 MCU 裸机无 C 运行时）→ 评估路线 2

**阶段 3（暂缓不动）**：动态数组增长、切片运行时边界长度——等合流方向明朗后按新模型设计（堆结构 ptr+len+cap）。
